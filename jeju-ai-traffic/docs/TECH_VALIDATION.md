**매칭 쟁점 (B단계 설계 검토):** 제주 교통정보는 **표준 노드·링크 ID** 기준이다. 상용 경로 API 응답은 자체 도로 ID나 좌표열(polyline)을 준다. 따라서 ① 경로 좌표열 ↔ 표준노드링크 형상의 **기하 매칭**이 필요하고, ② 표준노드링크 형상 데이터 확보가 별도로 필요하다. 정확도·구현 비용이 크다. MVP 대안: 경로 API가 자체 제공하는 구간 혼잡도가 있으면 그것을 1차로 쓰고, C-ITS 사건은 좌표 근접(버퍼) 매칭만 한다. 매칭 실패 구간은 PRD AC-005-03대로 '정보 미확보'로 표시한다.

## 9. 사용자 결정 필요 사항
1. **서비스의 상업성:** 광고·유료화 계획이 있는가? 카카오 제휴 필요 여부가 여기에 달려 있다(BLK-02).
2. **경로 공급자 1순위:** 권고는 카카오모빌리티, 대안은 TMAP. Google은 제외한다.
3. **C단계 실호출 승인 여부:** 승인 시 필요한 것
   - 카카오 개발자 계정과 앱 생성(기존 카카오맵 활성 앱 유무 확인)
   - 카카오모빌리티 길찾기 이용 권한(신청 절차가 있을 경우)
   - Cloudflare 계정(Free)
   - 공공데이터포털 활용 신청(제주 실시간 교통정보, 제주 C-ITS)
   - **비즈월렛·결제수단 연결 금지**를 조건으로 하고, 호출 상한(예: 공급자당 20건 이내)을 정한다
4. **IMPLEMENTATION_PLAN 2절 갱신:** Google 대신 국내 공급자를 후보로 바꾸는 것은 계획 변경이므로 사용자 승인 사항이다.

**쿼터 예산 (B단계 산정, 가정 포함):**
- 1회 모니터링 시간당 재평가 12회
- 재평가 1회 = 경로 호출 k회 (복수 경로를 옵션별로 받으면 k=3 가정) + 교통 호출 1~2회
- 카카오 일 10,000건 기준 약 **277 모니터링·시간/일**(k=3)
- 서버 측 사전 차단 임계값은 무료 한도의 **80%** 이하로 둔다(안전 여유분, PRD COST-002)
- 공급자 측 429 차단을 2차 방어선으로 쓴다(PRD 주의: 자체 카운터만으로 0원을 보장하지 않음)
