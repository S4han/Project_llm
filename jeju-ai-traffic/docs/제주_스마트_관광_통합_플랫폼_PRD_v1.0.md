## 1. 제품 개요
제주 관광객과 지역 이용자가 관광지, 숙박, 음식점, 카페 정보를 여러 서비스에서 각각 검색해야 하는 불편을 줄이기 위해, 비짓제주·한국관광공사 TourAPI·카카오 로컬을 결합한 통합 검색 모바일 웹을 구축한다. 서로 다른 출처의 동일 장소를 통합하고 출처·정보 최신성·정보 누락 여부를 표시한다. 지도와 외부 길찾기 연계를 제공하되 실제 내비게이션 경로 재현은 외부 서비스에 종속된다.

## 2. 문제와 목표
### 2.1 문제
- 관광지와 주변 숙박·음식점·카페 정보가 분산되어 여러 차례 검색해야 한다.
- 동일 장소가 출처마다 중복되어 비교가 어렵다.
- 일부 API가 실패하거나 무료 사용량이 소진될 때 검색 결과의 완전성을 알기 어렵다.
- 무료 API의 요금·할당량·저장·재사용 조건이 출처마다 달라 비용 및 약관 위반 위험이 있다.

### 2.2 사용자와 목표
- 1차 사용자: 제주 방문 관광객, 모바일에서 주변 장소를 찾는 이용자.
- 2차 사용자: 서비스 운영자(무료 한도·장애·안전 차단·알림 확인).
- 사용자 목표: 하나의 검색 화면에서 네 카테고리를 찾고, 위치·출처·지도 정보를 확인해 방문 결정을 내린다.
- 운영 목표: 월 유료 청구 없이 검색을 제공하고, 불확실한 비용·보안 조건에서는 안전하게 요청을 차단한다.

### 2.3 성공 기준
- 핵심 사용자 여정: 검색어 또는 현재 위치 입력 → 통합 결과 → 상세/지도 열기까지 완료 가능.
- 품질 지표: 검색 성공률, 카테고리별 결과 보유율, 중복 병합 오탐률/누락률, 출처별 최신성, 부분 결과 비율.
- 운영 지표: 외부 API 유료 청구 **0원**, 무료 한도 초과 호출 **0건**, 안전성 미확인 상태에서 외부 호출 **0건**, 차단·복구 이벤트 추적 가능.
- 수치형 성능·정확도 목표: 실제 API 및 파일럿 측정 전 임의 확정하지 않음; 출시 승인 시 계측 결과로 목표 설정.

## 3. 범위
### 3.1 MVP 포함(Must)
1. 모바일 웹 반응형 화면 및 제주 중심 통합 검색.
2. 관광지·숙박·음식점·카페 카테고리 필터.
3. 키워드 검색, 현재 위치 권한 요청, 위치 거부 시 수동 지역/검색어 입력.
4. 비짓제주·TourAPI·카카오 로컬 공급자 어댑터와 정규화 모델.
5. 중복 장소 판별 및 출처 추적, 검증 가능한 필드만 병합.
6. 결과 목록·장소 상세·지도/외부 길찾기 링크.
7. API별 무료 한도·예약·차단, 부분 결과 표시, Fail-Closed.
8. 운영자 인증 대시보드, 운영 이벤트·알림·이력 정리·서명 키 안전 관리.

### 3.2 MVP 제외
- 숙박 예약·결제, 음식점 주문·예약, 회원 포인트, 광고 상품 판매, 업체 CRM.
- 스마트시티 실시간 교통·IoT 데이터 통합, 고도화된 개인화 추천, AI 자동 여행 일정 생성.
- 지역 숙박·음식점 유료 마케팅 집행 및 광고주 관리 기능.

### 3.3 후속 확장
- 숙박·음식점 연계 마케팅, 제휴 쿠폰 및 지역 상권 프로모션.
- 스마트시티 데이터 연계 위치 기반 서비스.
- 사용자 동의 기반 개인화 및 여행 코스 추천.

- 데이터 출처별 이용약관이 서로 충돌하거나 결합·저장 권한이 불명확하면 해당 필드/소스를 저장·노출하지 않는다.

## 5. 표준 데이터 모델(설계 기준)
```text
Place {
  placeId, category, displayName, normalizedName,
  address, roadAddress, latitude, longitude,
  phone, description, imageUrls, externalLinks,
  sourceRefs[], fieldSources{}, lastSyncedAt,
  usagePolicy, confidence, availabilityStatus
}
SourceRef { provider, sourceId, fetchedAt, sourceUrl, policyVersion }
```
- 필드는 **내부 표준 필드**이며 특정 API에서 모두 제공된다는 뜻이 아니다.
- `category`: ATTRACTION / ACCOMMODATION / RESTAURANT / CAFE.
- 결측치는 임의 생성하지 않고 '정보 없음'으로 표현.
- 저장·캐시·이미지 재사용은 출처별 약관 검증 후 허용된 데이터에만 적용.

## 6. 중복 통합 및 검색 아키텍처
### 6.1 정규화·중복 처리
1. 각 소스별 어댑터가 원본을 표준 Place 후보로 변환한다.
2. 동일 출처의 고유 ID는 동일 장소 식별의 1차 기준으로 사용한다.
3. 출처 간에는 정규화된 명칭, 주소, 좌표 근접도, 전화번호 등을 결합해 후보를 생성한다.
4. 확실한 일치만 자동 병합하며 모호한 후보는 분리해 오병합을 방지한다.
5. 필드별 출처와 갱신 시각을 유지하고 약관 충돌 시 해당 필드 결합을 금지한다.
6. 거리 임계치·문자열 유사도 임계치는 검증용 샘플로 결정한다(임의 확정 금지).

### 6.2 요청 흐름
```text
모바일 웹
  → 검색 API(서버)
  → 공급자별 무료 한도·안전성 사전 검사 및 원자적 예약
  → 허용된 공급자에만 요청
  → 공급자별 응답 검증/정규화
  → 출처 정책에 맞는 중복 판별/병합
  → 부분 결과 여부·출처·최신성 표시
  → 결과 목록/상세/지도 연결
```
- 공급자별 실패 격리: 한 소스 실패 시 나머지 안전한 소스의 결과를 제공한다.
- 모든 소스 차단 시 신규 외부 호출 없이 안내한다.
- 검색 결과 없음과 소스 장애/할당량 차단을 구분한다.

## 7. 핵심 사용자 시나리오
### US-01 키워드 통합 검색
- 관광객이 '성산일출봉'을 입력하고 검색한다.
- 시스템은 허용된 공급자만 조회하고 장소 중복을 통합하여 출처가 명시된 목록을 제공한다.
- 완료: 관련 결과를 확인하고 상세를 열 수 있다.

### US-02 현재 위치 주변 검색
- 사용자가 위치 권한을 허용하면 주변 카페·음식점을 검색한다.
- 권한 거부/좌표 오류 시 수동 지역·검색어로 검색할 수 있다.
- 완료: 선택 조건과 결과 범위를 확인할 수 있다.

### US-03 장소 상세와 지도
- 사용자가 검색 결과를 선택해 이름·주소·좌표·가능한 연락처·출처·정보 최신성을 확인한다.
- 지도/외부 길찾기를 선택하면 지원되는 외부 지도 서비스로 이동한다.
- 완료: 장소 위치 또는 외부 지도 진입 가능.

### US-04 부분 결과
- 한 공급자가 장애·무료 한도·정책 미확인으로 차단된다.
- 다른 공급자의 안전한 결과만 제공하고 일부 정보가 누락될 수 있음을 알린다.
- 모든 공급자 차단 시 신규 외부 호출을 중단한다.

### US-05 운영자 확인
- 인증된 운영자가 공급자별 사용량·예약량·안전 상한·차단 사유·경고 이력을 확인한다.
- 관리자 확인은 자동으로 차단을 해제하지 않는다.

### US-06 서명 키 사고·복구
- 고위험 키 사고 의심 시 영향받는 키를 즉시 격리한다.
- 원인 분석, 안전성 검증, 관리자 승인, 승인 유효기간, 격리 상태 버전의 원자적 검증을 통과한 범위만 복구한다.

## 9. 운영 정책 기준선(OPS-AC001~595 주요 합의 요약)
### 9.1 비용·공급자 격리
- 월 0원 목표, 유료 호출 금지. 공급자별 무료 쿼터·비용 미확인 시 Fail-Closed.
- 요청 직전 사용량+예약량을 내부 안전 상한과 비교하고 원자적으로 예약.
- 실제 미전송이 입증된 예약만 환급. 안전 버퍼 수치는 제공자별 공식 한도 검증 후 산정.
- 공급자별 장애/차단을 분리하고 부분 결과를 안내.

### 9.2 경고·운영 이력
- 80% 및 차단 경고, 운영 대시보드와 무료 조건이 확인된 이메일 알림.
- 동일 경고 에피소드 중복 발송 억제, 이메일 최대 3회(최초/+1분/+5분) 시도; 무료 조건 불충족 시 대시보드로 대체.
- 운영자 확인은 기록만 남기며 강제 차단 해제 권한을 제공하지 않음.
- 운영 이벤트 90일 보관; 장애·경고 이벤트 및 직접 연결 상세 이벤트는 검증된 종료 시각+90일, 미종료는 삭제 금지.

### 9.3 이력 정리 및 잠금
- 일별 만료 이력 정리, 실패 시 30분 후 1회 재시도. 반복 경고가 열려 있으면 신규 자동 정리 일시 중지.
- 동일 정리 작업은 재개 시 작업 ID 유지, 실행 시도 ID 구분; 다음 날 미완료 작업 우선 재개, 누락 일자 소급 실행 금지.
- 작업 생성 시 삭제 대상 기준 시각 고정, 분할 정리·체크포인트 기록, 실제 삭제 사실 검증.
- 잠금 소유권·TTL·이전 실행 종료를 확인한 경우에만 안전 복구; 불확실하면 중지.
- 체크포인트 불일치나 저장 실패 시 정리 중지, 검증 가능한 실제 삭제 증거가 있을 때만 자동 정정.

### 9.4 이벤트 연결 및 동시성
- 하나의 상세 이벤트가 여러 사고에 연결되면 원본 1개를 유지하고 모든 연결 사고의 보관 기간이 끝나야 삭제.
- 삭제 전 연결 버전 재검증; 신규 연결과 삭제는 원자적으로 경합 처리.
- 이미 삭제된 이벤트에 대한 연결 요청은 거부하고 최소한의 실패 이벤트를 별도 기록.
- 서버 발급 논리 요청 ID로 실패 이벤트 중복 생성 방지, ID 만료 후 재요청 거부.

### 9.5 서명 토큰·키 보안
- 서버 발급 요청 ID·최초 생성 시각을 권위 있는 저장소에서 검증하고, 위변조 방지 토큰으로 발급 정보 정리 후 만료 요청도 거부.
- 최신 서명 키로 신규 발급, 이전 검증 키로 과거 토큰 검증. 이전 키는 관련 토큰 모두 만료되고 폐기 후에도 안전한 거부가 가능할 때만 폐기.
- 키 유출·무결성 손상·비인가 접근 등 고위험 징후 시 즉시 격리. 일반 만료·서명 불일치는 해당 요청 거부/기록하되 키 신뢰성 근거가 없으면 전체 격리하지 않음.
- 복구는 원인 분석·안전성 검증·인증된 관리자 승인 필수. 격리 상태 버전과 복구 실행의 원자성을 확인하고 상태 변경 시 승인 무효화.

## 10. 잔여 정책에 대한 AI 추천안 채택(사용자 위임)
### 10.1 복구 승인 유효기간
- **채택: A안.** 복구 승인에는 서버 발급 시각 기반 유효기간을 적용한다. 만료된 승인은 재검증·재승인을 요구한다.
- **설계 초기값(검증 전 제안): 15분.** 보안 운영 시뮬레이션과 운영 편의성 검증을 거쳐 출시 구성값으로 확정한다. 시간 검증 불가 시 복구 차단.
- 복구 승인은 격리 상태 버전·대상 키·검증 근거에 결속되고, 한 번 사용한 승인의 재사용은 금지한다.

### 10.2 남은 미결 정책 기본 의사결정 규칙
1. **보안/비용:** 안전성 미확인 또는 무료 한도 확인 실패 → Fail-Closed.
2. **데이터:** 공급자 이용약관/원본 필드 미확인 → 저장·병합·재배포 금지.
3. **성능:** 측정 전 SLA 수치 단정 금지; 파일럿 측정 후 배포 게이트로 확정.
4. **API 호출량:** 실측 트래픽과 공식 무료 쿼터로 공급자별 안전 상한 계산; 숫자 임의 설정 금지.
5. **토큰 ID 만료:** 서버 검증·키 수명·발급 이력 정리와 일관된 기간을 기술 검증 후 결정; 그 전 관련 신규 변경 작업 차단.
6. **운영 알림:** 무료 이메일이 불가능하면 인증된 대시보드 기록으로 대체, 무단 유료 전환 금지.
7. **관리자 권한:** 최소 권한, 서버 측 권한 검증, 감사 기록; 검증 우회·강제 해제 불허.
8. **키 보관:** 키 버전별 최소 접근권한·무결성 검증; 모든 관련 토큰 만료 및 폐기 후 안전 거부가 입증되기 전 삭제 금지.
9. **개인정보:** 위치 권한은 사용자 동의 기반, 목적 외 수집 최소화, 장기 위치 이력 기본 비저장.
10. **서비스 장애:** 부분 검색 결과 제공을 우선하되 안전하지 않은 소스는 호출하지 않음.

## 11. 비기능 요구사항
- 보안: API 키·서명 키 서버 보관, 클라이언트 비노출, 관리자 인증/인가, 로그의 비밀정보 마스킹.
- 가용성: 소스별 장애 격리 및 부분 결과; 전부 불가하면 정확한 제한 안내.
- 무결성: 예약량·이력 삭제·연결 변경·키 복구의 원자적 처리 검증.
- 개인정보: 위치 권한 최소 요청, 동의 거부 시 대체 경로, 불필요한 개인 식별·위치 이력 미보관.
- 접근성: 모바일 화면에서 키보드 접근·상태 안내·오류 설명 제공.
- 관측성: 공급자별 요청량·예약량·차단·오류·경고·복구 기록, 90일 이력 정책.
- 비용: 무료 한도 초과 시 신규 호출 금지; 무료 실행 조건 불명확하면 해당 작업 중지.

## 12. 권장 기술 아키텍처(구현 제안, 특정 서비스 확정 아님)
- 프론트엔드: 모바일 웹 SPA 또는 SSR 프레임워크.
- 백엔드: 서버 측 API 프록시 및 공급자 어댑터.
- 저장소: 무료 제공 범위 내에서 원자적 비교-갱신/트랜잭션이 **실제로 검증된** 데이터 저장소.
- 운영: 인증 대시보드, 무료 일정 실행, 조건부 무료 이메일.
- 지도: 외부 지도 서비스의 최신 약관·무료 한도 검증 후 연계.
- API 키/서명 키: 서버 측 비밀 저장소 및 버전별 권한 통제.
- 구체적 클라우드·DB·프레임워크는 무료 제공량·약관·원자성 검증 전 고정하지 않는다.

## 13. API 호출량 설계 원칙
- 공급자별 예상 호출량 = 검색 요청 수 × 요청당 공급자 호출 수 × 재시도 계수 − 허용된 캐시 적중에 의한 절감량.
- 캐시·재시도는 공급자 약관에서 허용한 경우에만 적용.
- 예약량 포함 사용량이 내부 안전 상한에 도달하면 해당 공급자 호출을 중단.
- 기준 기간·시간대·무료 한도·실제 과금 조건을 공식 자료로 확인하기 전에는 호출 가능 횟수를 확정하지 않는다.

## 16. 최종 결론
MVP는 제주 관광지·숙박·음식점·카페를 3개 데이터 소스로 통합 검색하는 모바일 웹이다. 검색·중복 통합·출처 표시·지도 연계와 함께 공급자별 무료 한도, 부분 결과, Fail-Closed, 운영 이력·안전한 삭제·서명 키 사고 복구를 필수 요구사항으로 둔다. 마케팅과 스마트시티 연계는 후속 확장으로 제외한다. 본 PRD는 기획 기준선으로 확정하되, 미검증 외부 사실은 출시 게이트로 분리한다.
