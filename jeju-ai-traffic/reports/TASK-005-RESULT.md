## 2. 구현 요약
- **호출 구성:** 카카오 추천(RECOMMEND)·최단거리(DISTANCE) 2회. 한라산 횡단(한쪽 위도 ≥ 33.38, 다른 쪽 ≤ 33.33)이면 1100고지·성판악 경유 2회 추가. 계획한 호출 수만큼 사용량을 한 번에 예약하고(`guardedCall`, cost 2 또는 4) 병렬로 호출한다.
- **결과 모으기:** 일부 호출만 실패하면 성공분을 준다. 모두 실패하면 ① 429 → 다음 KST 0시까지 차단 + 429 ② 장애 → 503(다시 시도) ③ 모두 경로 없음 → 400과 이유별 안내. 일부만 429면 성공분은 주고 이후 호출은 차단한다.
- **같은 경로 합치기·추천:** 거리 1% 이내 + 시간 120초 이내는 앞 순서만 남긴다. 예상시간(초) 최솟값 추천, 동률이면 거리 → 호출 순서. 차이는 원천 초 값으로 계산하고 표시만 분 반올림.
- **경로 없음 이유:** 카카오 `result_code` 102 → "출발지 근처에서 도로를 찾을 수 없습니다", 103 → "목적지 근처에서 도로를 찾을 수 없습니다. 주차장·입구 등…", 그 외 → 일반 안내.
- **화면:** 추천 경로를 맨 위, 나머지는 예상시간 순. 카드마다 예상시간·거리·추천과의 차이. 상단에 "10월 19일 16:05 조회 기준 · 카카오모빌리티 예상시간"(모의면 "모의 데이터"). 단일 경로면 "대체 경로 없음", 동률이면 안내 + '동률' 표시. 장애일 때만 '다시 시도' 버튼(한도·입력 문제는 버튼 없음). 출발지·목적지를 바꾸면 이전 결과를 지운다.
- **경로 이름 조정:** 계획의 '추천 경로'·'최단거리 경로'를 **'카카오 추천'·'최단거리'** 로 바꿨다. 동률 화면 캡처에서 이름이 '추천 경로'인 카드와 '추천' 배지가 다른 카드에 붙어 혼동되는 것을 발견했기 때문이다. 호출 방식 기준 이름이라는 승인 내용은 그대로다.
- **교통 상태:** `trafficStatus`는 `unknown`으로 두고 화면에 표시하지 않는다(TASK-006).

확인된 점:
1. 어댑터가 실제 응답(자동차 길찾기 GET, 경유지 길찾기 POST)을 정상 정규화했다. 좌표(`vertexes`)도 경로당 496~1,656개 받았다.
2. 같은 경로 합치기 규칙이 실제 값에서 서로 다른 경로를 합치지 않았다(예: A의 최단거리 43.0km와 516 경유 43.5km는 거리 1.2% 차이로 별개 유지).
3. **검색으로 고른 장소 좌표가 도로에서 멀면 경로가 나오지 않는다**(산 정상 등). 이유별 안내 문구를 추가한 근거다.
4. 같은 쪽 이동(B2)은 2회 호출로 경로 2개를 얻었다.

## 8. 남은 이슈
1. **도로에서 먼 장소 좌표.** 산 정상·해변 등 POI 좌표는 경로가 나오지 않을 수 있다. 지금은 이유별 안내로 처리한다. 장소 검색 결과의 좌표를 그대로 쓰는 한계이며, 주차장·입구로 보정하는 기능은 범위 밖.
2. **응답 크기.** 경로당 좌표 최대 약 1,700개(4개 경로면 수천 개)를 그대로 보낸다. 지도(TASK-006)에서 쓰기 위해 유지했으며, 필요하면 TASK-006에서 간소화를 검토한다.
3. 실제 배포 환경(Vercel)에서의 실호출은 미실시(배포 별도 승인). 배포 시 `ROUTES_PROVIDER=kakao`를 설정해야 실제 경로가 나온다.
4. 카카오 응답에 데이터 기준 시각이 없어 '조회 시각'만 표시한다(PRD AC-003-05는 둘 중 하나를 허용).
5. 빈도 제한·사용량 카운터는 인스턴스별(TASK-003과 같은 한계).
